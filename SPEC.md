1. Общая идея

Небольшое предприятие предоставляет рабочих для выполнения различных сельскохозяйственных работ у разных заказчиков.

Система должна заменить значительную часть ручного управления:

руководитель сейчас должен распределять людей;
сообщать им, куда и когда ехать;
понимать, кто где работает;
получать информацию о фактически отработанных часах;
учитывать работу каждого сотрудника;
рассчитывать, сколько денег необходимо каждому сотруднику;
видеть историю работы;
контролировать выданный инвентарь;
получать отчёты по людям, заданиям, объектам и заказчикам.

Система должна состоять из приложения для руководителя и приложения для сотрудников. При этом руководитель, сотрудник и бригадир не обязательно являются разными людьми. Один пользователь может одновременно быть, например, руководителем и сотрудником или руководителем и бригадиром.

Ключевой принцип: бригада не является самостоятельной бизнес-сущностью. Это временное или организационное объединение сотрудников внутри конкретного задания, созданное прежде всего для того, чтобы руководителю не приходилось взаимодействовать с каждым сотрудником отдельно.

2. Главный объект системы: задание

Основной рабочей единицей является Task / Задание.

Руководитель создаёт задание и указывает:

что нужно сделать;
какого заказчика это касается;
локацию, если она имеет значение;
каких сотрудников направить;
кто из них будет бригадиром, если нужен контактный человек.
Заказчик

У одного заказчика может быть несколько локаций.

Например:

Заказчик A:

ферма 1;
ферма 2;
поле 3;
склад 4.

При этом условия работы с заказчиком сейчас одинаковые для его локаций.

Локация

Локация является частью контекста задания.

Она может быть указана, а может быть несущественной для конкретного задания.

Ты отдельно отметил важный момент: в дальнейшем одно задание потенциально может быть связано с несколькими локациями, а одна локация может одновременно иметь несколько заданий.

Поэтому архитектура не должна искусственно предполагать, что:

одно задание = одна локация.

Это ещё один момент, который при детальном проектировании нужно будет оформить правильно.

3. Назначение людей

В одно задание руководитель может назначить любое количество сотрудников.

Например:

Задание:

Сбор урожая у клиента X, локация Y

Назначены:

Иван
Пётр
Сергей
Али
Хуан
Марко
и т.д.

Если взаимодействие с группой удобнее вести через одного человека, один из назначенных сотрудников получает статус бригадира для этого задания.

Важно:

Бригадир не получает принципиально другой статус сотрудника.

Он просто становится контактным лицом группы.

Поэтому модель должна позволять:

одному сотруднику работать самостоятельно;
нескольким сотрудникам работать группой;
группе иметь бригадира;
нескольким группам работать на одном задании;
отдельному сотруднику работать вместе с бригадой;
руководителю самому быть участником задания;
руководителю самому выступать бригадиром.
4. Что происходит после создания задания

После назначения людей система должна уведомить их о задании.

Если у задания есть локация, руководитель может выбрать:

отправить локацию бригадиру или не отправлять.

Если отправка включена:

бригадир получает push-уведомление;
открывает приложение;
видит задание;
видит соответствующую информацию о локации.

На первом этапе не требуется автоматически контролировать нахождение человека через GPS.

GPS рассматривается как опциональная будущая функция.

5. Работа в течение дня

Ты сознательно отказался от обязательного индивидуального таймера.

На первом этапе:

никакого таймера нет.

Также нет необходимости заставлять каждого из десяти работников отдельно отмечать начало и конец работы.

Предполагается реальная организационная модель:

люди приезжают на объект;
начинают работать;
делают перерыв;
заканчивают работу;
обычно группа работает одновременно.

Если возникает нестандартная ситуация, например человек ушёл раньше, его часы могут быть скорректированы руководителем.

6. Учёт рабочего времени

Это центральная функция системы.

Есть два возможных источника факта работы:

Сам сотрудник

Сотрудник может самостоятельно создать запись о своей работе.

Бригадир

Если несколько сотрудников работают вместе, бригадир вводит количество часов за группу одним действием.

Например:

Бригада:

Иван
Пётр
Сергей
Али
Марко

Бригадир вводит:

8 часов

Система создаёт индивидуальные записи для каждого из этих сотрудников.

Таким образом, пользователю не нужно пять раз выполнять одну и ту же операцию.

Но учёт остаётся индивидуальным.

Это принципиально важно.

Система не должна считать:

Бригада = один работник.

Она должна считать:

Бригада = способ удобного массового ввода данных для нескольких отдельных работников.

7. WorkLog

На текущем этапе ты выбрал модель:

один WorkLog = один сотрудник + один день.

То есть WorkLog представляет фактически отработанное сотрудником время за день.

При этом нужно учитывать твоё первоначальное требование:

видеть, где и над чем человек работал.

Поэтому окончательная модель WorkLog должна позволять получить информацию о том, какие задания/контексты были связаны с работой сотрудника в этот день.

Это особенно важно, потому что один сотрудник может в течение дня работать в разных местах.

Например:

Иван:

8 августа:

задание A, объект 1;
задание B, объект 2.

В итоговом отчёте должно быть видно оба места.

При этом для расчёта заработка учитывается индивидуальное количество часов сотрудника.

8. Кто является источником факта работы

Правило, которое ты сформулировал:

факт работы создаёт сам сотрудник либо бригадир за группу.

Руководитель не обязан каждый день создавать часы за всех.

Руководитель является контролирующей стороной.

То есть:

Сотрудник/бригадир → вводит факт работы

Руководитель → контролирует и при необходимости исправляет

Это и есть выбранная тобой модель ownership данных.

9. Исправление часов

Только руководитель может изменить количество часов после их создания.

Например:

Бригадир ввёл:

8 часов

Руководитель выяснил, что человек реально работал:

6 часов

Руководитель меняет значение на 6.

При этом система не должна молча переписывать историю.

Должно быть видно:

первоначальное значение;
новое значение;
кто изменил;
когда изменил;
желательно причина изменения.

Ты отдельно подтвердил, что история изменений обязательна.

Сотрудник и руководитель должны видеть, что значение было изменено.

10. Почему возникло расхождение по часам

Ты уже определил нормальную процедуру.

Проблема возникает, например, если:

сотрудник забыл бы отметить время;
сотрудник неправильно указал часы;
в будущем вернётся таймер, но человек его не включил;
человек ушёл раньше;
фактическое количество часов отличается от введённого.

В таком случае сотрудник или бригадир сообщает руководителю, а руководитель принимает решение и при необходимости корректирует запись.

Я не хочу  строить сложную систему автоматической проверки.

На объектах обычно присутствуют сотрудники заказчика, поэтому фактическое количество часов можно при необходимости проверить вручную.

11. Несколько бригад на одном задании

Система должна поддерживать ситуацию:

Одно задание:

Сбор урожая на объекте X

На нём работают:

Бригада A:

5 сотрудников;
бригадир A;
8 часов.

Бригада B:

7 сотрудников;
бригадир B;
6 часов.

И отдельно:

ещё один сотрудник;
7 часов.

Эти группы вводят данные независимо.

Но руководитель должен видеть общую картину по заданию.

То есть система должна уметь одновременно показывать:

индивидуальную информацию;
информацию по группе ввода;
суммарную информацию по заданию.
12. Сотрудник

В приложении сотрудник должен видеть прежде всего собственную информацию.

В частности:

назначенные задания;
необходимые локации;
свои отработанные часы;
историю работы;
отчёты, доступные сотруднику;
статус выплат;
информацию о начисленных деньгах;
выданный ему инвентарь.

Сотрудник пока не должен иметь возможности самостоятельно менять подтверждённые часы.

13. Бригадир

Бригадир получает всё, что получает обычный сотрудник, плюс возможность действовать как контактное лицо группы.

Основная дополнительная функция:

ввести количество часов сразу за всех сотрудников своей группы.

Например:

Сегодня работали 8 часов.

После этого система отражает 8 часов индивидуально у каждого участника группы.

Бригадир не является отдельным типом сотрудника в экономическом смысле. Это назначаемая роль/функция.

14. Руководитель

У руководителя наиболее широкие права.

Он должен иметь возможность:

Управление сотрудниками
создавать сотрудников;
назначать им ставку;
активировать/деактивировать сотрудников;
видеть их информацию.
Управление заданиями
создавать задания;
выбирать заказчика;
выбирать локацию/локации;
назначать сотрудников;
назначать бригадира;
менять задание;
видеть статус задания.
Контроль рабочего времени
видеть часы;
исправлять часы;
видеть историю изменений;
видеть первоначальное и изменённое значение.
Управление выплатами
видеть, сколько заработал каждый сотрудник;
видеть общую сумму за период;
учитывать авансы;
видеть статус оплаты.
Управление инвентарём
видеть, у кого какой инвентарь находится.
15. Ставки сотрудников

У каждого сотрудника есть индивидуальная почасовая ставка.

Например:

Иван: 9 €/час;
Пётр: 10 €/час;
Сергей: 12 €/час.

Тип работы пока не влияет на ставку.

То есть:

часы сотрудника × его ставка = начисленная сумма.

Я также допускаю , что в будущем может появиться оплата за выработку, а не только почасовая оплата.

Это значит, что архитектура не должна намертво зашивать единственный возможный тип оплаты.

Но для первой версии используется почасовая модель.


16. Изменение ставки

Руководитель указывает ставку при создании сотрудника.

Если ставка когда-нибудь изменится:

уже выполненная работа должна остаться по старой ставке;
новая работа должна рассчитываться по новой ставке.

Вероятность частых изменений ставки я считаю  практически нулевой, поэтому здесь не требуется сложная система управления тарифными договорами.

Но историческая ставка должна быть сохранена корректно.

17. Выплаты

Система должна позволять выбрать расчётный период.

Например:

1–15 августа.

И получить:

Сотрудник	Часы	Ставка	Начислено	Аванс	К выплате

Авансы уже входят в требования.

Статус оплаты также должен быть виден сотруднику.

Например:

начислено;
ожидает выплаты;
выплачено.

Точная модель бухгалтерской выгрузки пока не определена.

18. Заказчик и локации

Отдельно существует сущность заказчика.

Один заказчик может иметь много локаций.

Например:

Client A

→ Location 1
→ Location 2
→ Location 3

Руководитель должен иметь возможность смотреть:

По заказчику

Общее количество часов всех сотрудников на всех его объектах.

По локации

Количество часов, людей и заданий на конкретном месте.

По заданию

Кто был назначен и сколько времени отработал.

При этом одно задание может в будущем охватывать несколько локаций, поэтому связь Task и Location на этапе архитектуры нельзя слишком рано зафиксировать как строгое 1:1.

Минимальный набор, который 
уже согласован:

По сотруднику
сколько часов;
за какие дни;
где работал;

сколько заработал;
статус оплаты.
По заданию
какие сотрудники назначены;
какие группы/бригадиры;

какие задания;

Другие отчёты должны строиться из уже имеющихся данных, а не требовать отдельного ручного ведения.

20. Инвентарь


сознательно не 
превращать это в складскую систему.

Нужен очень простой учёт:

У кого что находится.

Например:

Иван:

пила;
секатор;
защитные очки.

Руководитель может открыть:

Инвентарь сотрудников

и увидеть список.

Либо открыть карточку сотрудника и увидеть его инвентарь.

История движения инвентаря на первом этапе не нужна.

21. Уведомления

Push-уведомления являются обязательной функцией.

В частности:

новое задание;
изменение задания;
назначение/изменение локации;
другие важные события, которые будут определены при проектировании.

Особенно важен сценарий:

Руководитель создаёт задание → назначает бригадира → бригадир получает push → открывает задание.

22. Offline-first

Работа в сельскохозяйственных условиях означает, что интернет может отсутствовать или быть нестабильным.



данные должны сохраняться локально и синхронизироваться при восстановлении связи.

То есть приложение не должно терять введённую информацию из-за отсутствия интернета.

Например:

Бригадир находится на объекте без связи.

Он вводит:

8 часов.

Приложение сохраняет информацию локально.

Позже появляется интернет.

Приложение синхронизирует запись с сервером.

Ты не ожидаешь серьёзных конфликтов синхронизации, но лог изменений всё равно обязателен.

23. GPS

GPS не является обязательной частью первой версии.

Возможная будущая функция:

определить местонахождение сотрудника;
проверить нахождение на локации;
подтвердить начало/окончание работы;
использовать геозону.

Но сейчас система должна работать без GPS.

То есть архитектура должна позволять добавить его позже, но GPS не должен усложнять первую версию.

24. Таймер

Таймер также исключён из первой версии.

Первоначально рассматривалась автоматическая фиксация начала/конца работы, но ты решил, что для текущей организации работы это ненужное усложнение.

В будущем таймер можно вернуть.

Если его вернуть, ручной ввод часов должен оставаться механизмом исправления нестандартных ситуаций:

человек забыл включить таймер → в конце дня указывает фактическое количество часов.

25. Аудит

Для системы принципиально важен Audit Log.

Особенно для финансовых данных и рабочего времени.

Если руководитель изменил:

8 часов → 6 часов

система должна сохранить:

кто сделал изменение;
когда;
какое значение было;
какое стало;
какую сущность изменили;
какое поле изменили.

Это позволит в любой момент восстановить историю.

27. Что система должна позволять получить в итоге

Руководитель должен открыть систему и ответить практически на любой операционный вопрос, используя уже имеющиеся данные:

Кто сейчас назначен на это задание?

Где работают мои сотрудники?

Кто является контактным человеком этой группы?

Какие задания выполняются у этого заказчика?

Сколько людей работало на этой локации?

Сколько часов отработал Иван?

Где Иван работал в течение периода?

Сколько часов было выполнено для конкретного заказчика?

Сколько часов было выполнено по конкретному заданию?

## 1. Масштаб до 30 человек

Это сильно упрощает жизнь: никакой оптимизации, очередей, кэшей. Один дешёвый VPS. При таком масштабе можно даже стартовать на **SQLite** (файл-база, ноль администрирования) — для ≤30 пользователей её хватит с запасом, а деплой становится тривиальным. Переезд на Postgres при необходимости — задача на день.

## 2. Переименование «бригадира»

Согласен, «бригадир» вводит в заблуждение — звучит как должность. По сути это **«учётчик»** (в системе: `reporter`) — человек, который отправляет часы за группу. Варианты для интерфейса по языкам: рус. «старший» / «учётчик», укр. «старший», исп. «encargado». В коде и базе — нейтральное `is_reporter`. Это просто флаг в назначении на задание, как и договаривались.

## 3. Три языка (ru / uk / es)

Закладываем i18n с первого дня — это дёшево сейчас и мучительно потом:
- у пользователя поле `lang`;
- ни одной строки текста в коде — всё в файлах переводов (`ru.json`, `uk.json`, `es.json`);
- переводы файлов — идеальная работа для ваших дешёвых агентов.

## 4. Telegram Mini App для всех — да, это правильный ход

Mini App — это веб-приложение внутри Telegram. Значит **один интерфейс на всех**: руководитель видит свои экраны, работник свои — по роли. Не нужно делать «панель отдельно, бот отдельно». Бот остаётся только для push-уведомлений с кнопкой «Открыть» → Mini App.

Один нюанс — **offline**: обычное сообщение боту Telegram сам отправит при появлении связи, а Mini App без интернета не откроется. Решение: оставить в боте текстовую команду-дублёр для ввода часов (учётчик пишет боту «8» — часы записаны всей группе по активному заданию). Это ~50 строк кода и закрывает главный offline-сценарий.

Итог: **Mini App (весь интерфейс) + бот (уведомления и аварийный ввод часов)**.

## Схема базы данных

```
users            id, tg_id, name, phone, lang(ru/uk/es), hourly_rate,
                 is_manager, is_active, created_at
clients          id, name, notes, is_active
locations        id, client_id → clients, name, address,
                 lat, lon (nullable — задел под GPS)
tasks            id, title, description, client_id → clients,
                 status(draft/active/done/cancelled),
                 date_start, date_end, created_by → users
task_locations   task_id → tasks, location_id → locations        -- many-to-many
task_groups      id, task_id → tasks, reporter_id → users        -- группа внутри задания
task_assignments id, task_id → tasks, user_id → users,
                 group_id → task_groups (nullable = работает сам по себе)
work_entries     id, user_id → users, task_id → tasks,
                 location_id (nullable), work_date, hours,
                 rate_snapshot, pay_type('hourly'),
                 entered_by → users, created_at
advances         id, user_id → users, amount, date, comment, created_by
payouts          id, user_id → users, period_start, period_end,
                 gross, advances_total, net,
                 status(accrued/pending/paid), paid_at
inventory_items  id, name, holder_id → users (nullable = на складе), notes
audit_log        id, actor_id → users, entity, entity_id,
                 field, old_value, new_value, reason, created_at
```

Ключевые свойства (проверяйте, чтобы агенты не «упростили»):
- `task_locations` — отдельная таблица: задание ↔ локации many-to-many (ваше критичное требование);
- `task_groups` даёт несколько групп + одиночек на одном задании;
- групповой ввод часов = N строк в `work_entries` с одинаковым `entered_by`;
- `rate_snapshot` копируется из `users.hourly_rate` в момент создания записи — смена ставки не трогает историю;
- `work_entries` никогда не удаляются: изменение = UPDATE + запись в `audit_log`;
- все отчёты из п. 19 — это SELECT-запросы по этим таблицам, отдельных сущностей не нужно.
